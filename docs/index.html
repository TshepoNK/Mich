The Belief

The test was never
the problem. The model was.

Every testing tool built in the last 20 years shares the same assumption: a test is a script. A script that clicks element A, checks element B, and breaks when either moves. That assumption made sense when UIs were static. Today, it's structurally incompatible with how software is built.

🔄

UIs change constantly. Scripts don't adapt.

A design sprint, a rebrand, a component library upgrade — any of these can silently invalidate hundreds of tests. The script has no way to know what it meant.

🧱

Code as the only language of testing

The most valuable testers — those with deep domain knowledge, business understanding, regulatory expertise — are locked out because the tools speak only JavaScript.

📉

Maintenance cost scales with product velocity

The faster a team ships, the more tests break. At scale, test maintenance consumes 30–50% of automation engineering time. This isn't a tooling problem — it's a model problem.

🔇

Failures tell you nothing meaningful

A payment regression and a renamed CSS class look identical: a red test and a stack trace. The script knows what broke. It has no way to know why it matters.

🎲

Flakiness is endemic, not accidental

Race conditions, animation timing, network variability — these are structural properties of modern apps. Band-aids like retry() and waitFor() don't fix the model.

💡

The alternative: tests that pursue goals

What if a test wasn't a script at all? What if it was a goal — "the user should be able to check out" — and the system figured out how to verify it, every time, regardless of what changed?

How it works

Brief it. It runs.
You read the report.

Orion operates like a tester you can brief in plain English and trust to act independently. You set the scenario. It owns the execution.

1

Brief the scenario

Describe the user journey in plain English. "A new user signs up and reaches their dashboard." That's enough.

2

Orion builds the test

The Orchestrator agent maps the scenario to steps. No test scripts required. No selectors to choose. No code to review.

3

Agents execute it

Flow, Observe, and Memory agents navigate the live app, monitor network and console, and record what they learn for next time.

4

Read the report

A business-level summary lands: what passed, what broke, whether it's a real regression or noise, and what the team should do next.

Briefing Orion

If you can describe it,
Orion can test it.

A brief is just a user journey written out. Not a test script — a description of what a real user does and what should happen. Write it the way you'd explain it to a new colleague.

  • → No programming background required. If you can write a user story or an acceptance criterion, you can brief Orion.
  • → Orion builds the execution plan. You describe the journey. Orion decides which elements to interact with and how.
  • → Briefs survive UI changes. When the app is updated, Orion adapts the execution — the brief you wrote stays valid.
  • → Reviewable by anyone. A BA can read a brief and verify it captures the right behaviour. No code to decipher.
# A brief — not a test script
Scenario: New user signs up successfully URL: https://your-app.com/signup
Given I am on the sign up page When I fill in my name, email and password And I click "Create account" Then I should see a welcome message And I should land on the dashboard And url should contain /dashboard
✓ Orion handles the how. You own the what.
# Even simpler — just the steps
test: User signs up and reaches dashboard url: https://your-app.com/signup
steps: - "fill in name, email and password" - "click Create account" - "I should see a welcome message" - "url should contain /dashboard"
✓ Reads like a sticky note. Runs like a test suite.
Agent Modes

One agent. Two minds.

Orion operates in two modes simultaneously: the precision of a senior QA engineer and the business reasoning of a BA. Most tools only do the first. Neither does both.

🧪
Mode 1

Tester Mode

Acts as a meticulous QA engineer. Navigates the app, executes every step of the scenario, monitors network calls and console errors, and validates outcomes against intent.

✦6-strategy element resolution — never relies on a single selector
✦Self-healing when the UI changes — adapts strategy, keeps going
✦Network-aware assertions — validates API responses, not just pixels
✦Memory that compounds — each run makes the next run smarter
📋
Mode 2

BA Mode

Acts as a business analyst reviewing the outcome. Translates technical failures into business impact. Distinguishes regressions from noise. Identifies what the team actually needs to act on.

✦Business-level failure brief — not a stack trace, a post-mortem
✦App bug vs test drift classification — separates real regressions from noise
✦Likely-cause attribution — links failure to recent PRs and code changes
✦Pattern detection — flags recurring failure signatures across runs
Capabilities

What the agent does
on every run

🧭

Human-like navigation

Orion reads the interface the way a tester does — by aria role, visible label, screen region, and context. Not by CSS paths that break when a class name changes.

🔁

Autonomous self-healing

When a UI element moves or is renamed, Orion escalates to the next strategy, succeeds, and logs the change. The test stays green. The team gets a low-priority notice.

📡

Network intelligence

Every step is correlated with XHR and fetch traffic. Orion can verify that the right API calls happened — not just that the right pixels appeared.

📋

BA-grade reports

Failures are reported as incident briefs: user journey impacted, business severity, likely root cause, suggested next step. Readable by any team member.

🧠

Compounding memory

Every run updates Orion's knowledge of the app. Which strategies work for which elements. Which steps tend to flake. Which failure patterns have appeared before.

⚡

LLM reasoning engine

With an Anthropic API key, Orion's BA mode is powered by Claude Sonnet 4.6. Without one, deterministic briefs still give you structured, actionable output.

Selectors become irrelevant

Orion stores a multi-modal element fingerprint — not a CSS selector. Each interactive element is known by its aria role, visible text, screen region, and network trigger.

Strategies are ranked by confidence. When a developer renames a component, Orion tries the next strategy, succeeds, updates its map, and the test stays green. CI never sees red.

1

Primary strategy fails

CSS selector .checkout-btn not found — developer refactored the component.

2

Agent escalates to text strategy

Locates button with visible text "Complete Purchase" in the expected screen region. Confidence: 0.97.

3

Test passes. CI stays green.

Memory Agent logs the stale selector, promotes text strategy. A low-priority notice is queued for the team.

The Architecture

The Contrast

What a goal looks like
vs. what a script looks like.

Both verify the same user flow. One breaks when a class name changes. The other doesn't know what a class name is.

Script-based testing
// 17 lines of brittle, selector-dependent code
test('user can reset password', async ({ page }) => {
  await page.goto('/login');
  await page.waitForLoadState('networkidle');
  await page
    .locator('[data-testid="forgot-link"]')
    .click();
  await page.waitForURL('**/forgot-password');
  await page
    .locator('#email-input')
    .fill('test@example.com');
  await page
    .locator('[type="submit"]')
    .click();
  await expect(page
    .locator('.success-message'))
    .toBeVisible({ timeout: 5000 });
});
Goal-based testing — Orion (YAML)
# 7 lines. No selectors. Self-healing.

test: User can reset their password
url: https://your-app.com/login

steps:
  - "click the Forgot password link"
  - "type \"test@example.com\" into email"
  - "submit the form"
  - "I should see a confirmation message"
  - "url should contain reset-sent"

Get Started

Up and running in 3 steps

No account. No cloud signup. No configuration files. Runs locally on Chromium.

Step 1 — Install
$ npm install @oriontest/orion
Step 2 — Install Chromium
$ npx playwright install chromium
Step 3 — Run an example
$ npx orion run examples/example-domain.orion.yaml
Add --headed to watch the browser. Set ANTHROPIC_API_KEY for LLM-powered failure briefs.
